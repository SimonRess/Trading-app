# Design: Roadmap — Next Versions

**Status:** Approved by product owner 2026-07-27 (nothing here implemented yet)
**Last updated:** 2026-08-02

**This is the single source of truth for planned-but-unbuilt work.** It was assembled from `docs/prd.md`'s former Feature Backlog section and `docs/00_project_structure.md`'s former "Open backlog" subsection, plus `docs/design/feature-brainstorm.md`'s findings and one new item requested directly (moving supply/demand off the trading screen). Both source sections were removed once their content landed here, since maintaining the same items in multiple places let them drift out of sync with each other. `feature-brainstorm.md` remains a separate supporting doc (deeper rationale for the v1.2/v1.3 UX items) rather than being folded in, since it's a narrower playtest-findings writeup, not itself a backlog.

When scope changes — a new idea, a reprioritization, an item shipping — edit **only this file**. `docs/00_project_structure.md` §4b then gets a new ✅ line once something actually ships; `docs/prd.md` only changes if the shipped feature alters vision/scope/non-goals.

## v1.2 — Trading screen slimdown + UX polish

Low-risk, high-value UI work. No new game mechanics, so no `src/game/` changes and minimal test risk.

1. ✅ **Move Supply/Demand columns off the trading table, onto the City info screen.** Shipped: the Trading Post table is now `Good | Price | Stock | Buy | Sell` (was `Good | Price | Stock | Supply | Demand | Buy | Sell`) in both City-view and List-view; the Town Hall panel gained a per-good, read-only `Good | Supply | Demand` table for the selected city. Extracted a shared `src/ui/TradeTable.svelte` component (used by all 4 previous copy-pasted table instances — City-view in-port/no-ship and List-view in-port/at-sea) so the two views render the same markup instead of hand-synced duplicates, closing the duplicate-edit bug pattern that bit the i18n pass and the bulk-price fix. Verified live (Playwright): headers correctly show `Good, Price, Stock, In hold, Trade` with no Supply/Demand; bulk-buy price preview still updates correctly after a purchase (the exact area the earlier reactivity bug lived in); Town Hall's new table renders 5 correct supply/demand rows. No `GameState`/`game/` changes.
   - **Not done**: the broader `src/ui/App.svelte` split into `screens/`/`panels/`/`shared/` (the file is still ~1,930 lines) — only the trading-table piece was extracted. `App.svelte` is smaller and the worst duplication is gone, but the full split remains open for a future pass if the file's size keeps causing friction. See `docs/audits/2026-07-28-architecture-and-claude-code-review.md` finding #1.
2. ✅ **Header turn counter** — now shows "Turn N" instead of "Turn N/999999" (feature-brainstorm #1). Also fixed the season-info popup, which still said "At 999999 turns total, this game runs 249999.75 years" — the actual root cause behind the misleading header; `T.seasonInfoText` is now a plain string explaining there's no turn limit (win = Mayor, lose = death without heir or bankruptcy).
3. ✅ **Distinct ship vs. city map icons** (feature-brainstorm #2). Root cause was two things stacking, not just shared iconography: `SHIP_COLOR` (`0xc8a860`) and `CITY_COLOR`/`CITY_RING_COLOR` (`0xd4a843`/`0xf0dca0`) were near-identical gold tones, and a docked ship's marker was offset only 22px above its home city's icon — less than the city's own 15px-radius selection ring, so the two visually merged into one blob (confirmed via a live screenshot before fixing). Ships are now a distinct blue (`0x6fa8d0`/`0xbfe4ff` selected) and the docked-ship offset increased to 34px. Verified live: the two icons are now clearly separate at Lübeck's default zoom.
4. ✅ **Drop redundant qty-1 total on Buy/Sell buttons** (feature-brainstorm #3) — `T.buyBtn`/`T.sellBtn` now show plain "Buy"/"Sell" at qty 1, only including the `(total M)` parenthetical once qty > 1 makes it diverge from the adjacent Price column.
5. ✅ **"Sell all" quick action** next to Sell when in port (feature-brainstorm, small UI polish) — new button in `TradeTable.svelte` dispatching a `sellAll` event; `App.svelte`'s `sell()` gained an optional quantity-override parameter so `sellAll()` can sell the ship's full held quantity of that good in one action. Verified live: correctly zeroes out held cargo and updates cash.
5a. ✅ **Decided a test policy for `src/ui/`/`src/render/`** (audit #3) — documented in `CLAUDE.md`'s Testing section rather than left implicit: no component-test infrastructure exists yet (`vite.config.test.ts` only picks up `.test.ts` under a `node` environment, no jsdom/`@testing-library/svelte`), so reactivity-sensitive UI changes must be manually verified live as part of the same change, with what was verified noted in the commit/PR. `TradeTable.svelte` is named the first candidate for real automated coverage if that infrastructure gets added later.
5b. ✅ **Enforced `/check-conventions` against v1.2's diff** (audit #9) — ran all 8 checks manually against the full `origin/main..HEAD` diff. 7/8 clean; one finding: `TradeTable.svelte` is PascalCase, which the literal CLAUDE.md rule ("kebab-case for all files") flags, but it matches every existing Svelte component (`MapView.svelte`, `CityView.svelte`) — a gap in the rule's wording, not a real deviation. Fixed by updating CLAUDE.md's Code Conventions and the `/check-conventions` command itself to state the `.svelte`-PascalCase exception explicitly, so this ambiguity doesn't recur.

## v1.3 — Dynasty Chronicle + market memory

Player-facing history/feedback features. Mostly UI-layer, reading existing state rather than adding new mechanics.

6. ✅ **Dynasty Chronicle** — persistent `GameState.chronicle: string[]` logging succession events, surfaced as a read-only panel in the Merchant's House (feature-brainstorm #1, `design/family-succession.md` "Dynasty Chronicle"). Seeded with a founding entry at New Game; appends at every succession resolution point (auto-succession, `executeChooseHeir`, no-heir game over). Additive save field, no schema bump (defaults to `[]`). 2 new unit tests + 2 assertions added to existing succession tests. Verified live: genesis entry renders correctly in the Merchant's House panel. Scoped to succession only for this pass, not rank-ups/events/births — see the design doc for why.
7. ✅ **Price history / trend sparkline per good** — client-side only (feature-brainstorm #3). New `src/ui/Sparkline.svelte` (pure presentational, no game-logic imports) plotting a small inline SVG line; `App.svelte` tracks the last 10 turns' `currentPrice` per city/good in a UI-local `priceHistory` buffer (not `GameState` — no schema impact), rebuilt immutably each recorded turn rather than mutated in place, given this project's history of Svelte missing in-place-mutation updates (the bulk-price and label-overlap bugs). Shown as a 4th column on the Town Hall's Supply/Demand table. Verified live: 5 distinct trend lines render after several End Turns, and switching the Town Hall's city selector shows genuinely different per-city histories.
8. ✅ **Achievements / milestones log** — new `GameState.achievements: AchievementId[]` (`design/family-succession.md` "Achievements", feature-brainstorm #4), shown as badges above the Chronicle in the Merchant's House. 5 milestones (net worth ×2, first ship lost, first Mayor, second generation), evaluated by a pure `evaluateAchievements()` called from both `resolveTurn` and `executeChooseHeir`. Unlike the Chronicle, stores stable ids (not English text), so badges are properly localized via `i18n.ts`. "Survived a pirate Victory" (a brainstorm example) was dropped — not reliably diffable from top-level `GameState` without threading a new signal through `event-system.ts`. 11 new unit tests. Verified live: milestone fires in the turn summary and the badge appears afterward.
9. ✅ **Ship convoys** (redefined 2026-08-02, replacing the earlier "saved/repeating trade routes" scope below; fully specified 2026-08-02 in `design/ship-convoys.md`, implemented 2026-08-02) — group several ships into a convoy so the fleet overview shows one entry per convoy instead of one per ship. Shipped:
   - `src/game/systems/convoy-system.ts`: create/add/exclude/dissolve, convoy-wide destination (slowest member's travel time applied uniformly, gated on every member's `canDepart`), convoy-wide posture, and `PROPORTIONAL_DISTRIBUTION`-backed convoy buy/sell (one `resolveTradeStepped` call, then distributed — the strategy type is swappable).
   - `combat-system.ts`'s `resolveConvoyCombat`/`convoyCombatPower`: pirates engage a convoy as one unit (summed power, one posture modifier, one roll), but `event-system.ts` applies the outcome's durability/cargo loss independently per member, so a defeat can sink a weak member while stronger ones survive; a convoy dropping below 2 members auto-dissolves.
   - 8 new `GameAction` variants + `LocalGameClient` wiring; repair/crew/cannons stay per-ship, reached by drilling into a member (which also blocks auctioning a still-convoyed ship — `executeAuctionShip` now refuses until excluded).
   - UI: new `src/ui/FleetList.svelte` (grouped/collapsible convoy cards + drill-down + Exclude, shared by both the List-view sidebar and the City-view Harbor panel), a "Group into Convoy" checkbox flow, `TradeTable.svelte`'s new optional `convoyCargo`/`convoyCargoSpace` props, and convoy-wide destination/posture/dissolve controls in the Harbor panel and List-view trade panel.
   - 44 new unit tests (`convoy-system.test.ts` plus additions to `combat-system.test.ts`, `turn-system.test.ts`). Verified live (Playwright): grouped 2 ships into a convoy, drilled into members, set a convoy-wide destination, bought goods as a convoy (single stepped trade, proportional distribution confirmed by in-hold totals) — see `ship-convoys.md`'s "Implementation Status" for the two scope narrowings (no per-ship Shipyard duplicate for convoy members in the List-view trade panel; no travel-time preview on convoy destination buttons).
   - The original "saved/repeating trade routes" idea (auto-fill next turn's buy/sail/sell orders until cancelled, feature-brainstorm #2) is **not dropped** — moved to item 9c below as its own, smaller, still-unscheduled idea, since it solves a different problem (turn-to-turn repetition for one ship) than convoys (fleet-panel clutter + multi-ship coordination) and there's no reason grouping them under one number should hold either back.
9c. **Saved/repeating trade routes** (demoted from item 9, unchanged in substance) — auto-fill next turn's buy/sail/sell orders until cancelled (feature-brainstorm #2). Still needs its own design doc before starting; not yet scheduled to a specific version.
9b. ✅ **Second marriage partner type** — "the Alderman's Daughter" (`design/family-succession.md` "Marriage"), gated on `minNetWorth: 6000` (reputation gift instead of goods, wiring up the previously-unused `PartnerType.hasStatus` field). Merchant's House now lists every currently-eligible offer instead of one hardcoded button. 8 new/updated unit tests. Verified live (Playwright + a save-file wealth injection, since 6,000 net worth isn't reachable quickly by normal play): only the Fisherman's Daughter shown at New Game's ~4,660 net worth; both offers shown once wealthy; marrying the Alderman's Daughter correctly deducted 2,000 Mark and added +10 Hamburg reputation.
   - **Open task, not attempted here**: further partner types (political-rank-gated, or one bringing a ship — `PartnerType.ships` is reserved but unwired), a female-player-facing partner roster, per-partner marriage odds, and any ongoing (not just one-time) marriage mechanics. See `family-succession.md`'s new "Open task" note.

## v1.4 — Gameplay depth: stores & agents

The single biggest "targeted v1.1, never built" gap from the original vision (`prd.md` #3). Bigger effort, deserves its own ADR before implementation given it's a new core system (permanent per-city inventory + hired-agent skill/loyalty simulation).

10. ✅ (stores half) **Stores & agents in cities** (`prd.md` #3). Recon pass (`13a` below) confirmed this splits into two separable pieces. **Stores shipped** (2026-08-06): goods storage — owned-warehouse capacity, rented overflow up to a per-city cap, direct/ship/convoy store trading — per `docs/design/city-stores.md` (ADR-024). Agents (autonomous NPCs with skill/loyalty) remain unscoped, deliberately sequenced after stores per the recon report — this item stays open until agents ship too.
11. **Per-city warehouse income/price variance**, since it's closely related storage/economy surface area (`prd.md` #10) — `city-stores.md`'s new `CityDefinition.warehouseCapacity` (total warehouses per city, scaled by population) is itself a per-city variance point this item may want to build on.
11a. **Require physical presence for City Store trading** — flagged during v1.5's post-ship review (2026-08-06): `STORE_BUY_GOOD`/`STORE_SELL_GOOD` (`city-stores.md`, `store-system.ts`) currently let the player trade directly against any city's market with no ship there and no warehouse owned there, matching the pre-existing (also unrestricted) `executeBuyWarehouse` precedent but effectively letting half the trading loop skip the game's core "sail there, take the risk" mechanic entirely. Explicit product-owner decision (2026-08-06): remote store access should eventually be blocked — likely gated on owning at least one warehouse in that city (a "you need a foothold to do business" requirement), though the exact gate (warehouse ownership vs. a ship having ever docked there vs. something else) isn't decided yet. Deliberately left unimplemented for now (remote trading stays as-is) — needs its own short design pass before implementation, most naturally scoped as a small addendum to ADR-024 rather than a new ADR.
12. **Combat loot realism** — simulated enemy fleet instead of a fixed loot pool (`prd.md` #1), natural follow-on now that combat (v1.0) has shipped and stabilized.
13. **Ability to initiate combat** — hunt pirates for loot/reputation (`prd.md` #2).
13a. **Use a dedicated `Explore`/`Plan` subagent pass before scoping the ADR** (audit #10) — this is the first roadmap item big enough to justify it: a new core system (permanent per-city inventory + hired-agent skill/loyalty simulation) benefits from a focused reconnaissance pass that doesn't consume the main session's context before the real design work starts.

## Engineering/process items (not version-bound)

From `docs/audits/2026-07-28-architecture-and-claude-code-review.md`. These aren't player-facing features so they don't get a version number — they're small, independent of game content, and safe to do whenever, rather than waiting on a release. Listed here (not left only in the audit file) so they're tracked in the same single place as everything else, per this doc's own point about backlog drift.

- **Fix `CLAUDE.md`'s architecture diagram** (audit #2) — it documents Svelte stores in `src/game/state/` that don't exist; the real state lives in `LocalGameClient`. Doc-only fix.
- **Add a `build` step to `ci.yml`** (audit #6) — currently only `deploy.yml` runs `npm run build`, so a build-only failure can pass CI and only surface at deploy time on `main`.
- **Delete the 8 already-merged stale `claude/*` branches** (audit #5), local and remote.
- **Pick one canonical project name** (audit #7) and use it consistently across `package.json`, `index.html`, and doc headers.
- **Add `eslint` to the `PostToolUse` typecheck hook** in `.claude/settings.json` (audit #12), so lint violations (including the architecture-boundary `no-restricted-imports` rule) are caught at edit-time, not just at the end of a task.
- **Add a `/ship` command** (audit #11) capturing the repeated check-suite → docs → commit → push → deploy sequence, the same pattern as the existing `/new-adr`/`/new-design` commands.

## Open challenges to watch across this whole plan

- **City-view/List-view markup duplication** — two independently-edited copies of most panels has caused missed-edit bugs twice this session (i18n pass, bulk-price fix). Now scoped into v1.2 item 1 (shared `TradeTable.svelte` + `App.svelte` split), not just flagged.
- **Save-schema versioning** — v1.3's Chronicle field is the first `GameState` shape change since localization shipped; confirm `docs/design/save-file-schema.md` (referenced in CLAUDE.md, not yet created) exists before it lands, or create it then.
- **Game-logic/UI message boundary** — v1.5's narrative-string refactor is the same architectural seam CLAUDE.md's Hard Rule 1 protects; do it once, properly (message keys + params), rather than as an incremental patch, since it touches every system file.
- **Effort sizing** — v1.4 (stores & agents) and v2 (expeditions, hotseat) are the two biggest single items in this whole plan; each should get its own ADR/design doc and be split into sub-tasks before implementation starts, per `00_project_structure.md`'s planning workflow.
